# Prepared observation plan for the rebuilt product

Owner: Codex. This is a ready-to-use observation protocol and iteration guide. No outreach, invitation to a real person, sales message or payment request has been sent. The earlier market analysis remains the decision record; automated product tests do not prove willingness to pay.

## Hypothesis being tested

A coach who already has clients can deliver a usable plan and review what happened with less explanation and administrative effort. The client gets a workout they can follow immediately. Rafik does not promise the coach new leads. The public sample also permits a separate direct-client test without building a second product.

## Five-minute demonstration

1. Open the public sample on a phone-sized browser. No signup. Start a session, change a weight, record a set and reload. Show the retained values.
2. Finish, then optionally save to an account. Explain the difference between device save and server acknowledgment only when that status matters.
3. Open the synthetic coach account. Start a plan from the populated starter, adjust one exercise, preview, and publish.
4. Create an invitation for a synthetic inbox address. Open it in another browser context; verify the code from local Mailpit and accept.
5. Complete a session, leave a note, then save a coach reply. Reopen the client result and show the reply.

The sample accounts are visibly labelled and all activity is synthetic. Do not describe them as customer proof.

## Task observation scripts

Give the participant the goal; do not narrate button names or rescue them before recording the point of confusion.

| Participant | Prompt | Record |
|---|---|---|
| New client | “You have a pair of dumbbells. Find a session and record the first set you perform.” | Time to useful prescription, time to first real set, missed next action, unnecessary signup expectations |
| Returning client | “You were interrupted halfway through. Continue where you left off and finish.” | Lost work, resume recognition, unit/repetition mistakes, completion confidence |
| Invited client | “Your coach sent this link. Open your plan and tell them how the session went.” | Email mismatch, code delivery, plan context, effort to send a useful note |
| Coach | “Adapt this starter to a client you already train, then share the plan.” | Setup time, retyping, field confusion, preview usefulness, manual help required |
| Coach after use | “Find the session needing attention and give a useful reply.” | Review time, ability to distinguish prescribed vs actual, unnecessary navigation |

Run English and Arabic task sessions separately where practical. Include people with low tolerance for new apps. Record unsuccessful attempts as outcomes; a download or a meeting is not activation.

## Actual-use protocol

Use the predeclared small-cohort experiments in `docs/revival/00-market-and-business.md`: initially up to ten qualified coaches, seeking at least three concrete commitments with real plans and nominated clients. Do not require this recruitment before fixing observed interface failures; the local core is already built.

Offer text for a future approved outreach: “Bring one training plan and a small group you already coach. We will set up a client-ready workout link, then observe whether clients complete sessions and whether reviewing them takes less effort.” Clearly state duration, included setup, supported exercises, and what the paid continuation would cover before starting. This is a draft, not an outgoing message.

Pricing is still an experiment. Prepare one concrete continuation price after measuring setup/support effort and the coach's actual use; record amount, currency, allowance, setup scope, decision date and payment evidence. Do not present competitor prices as Rafik's proven willingness-to-pay. Avoid charging both coach and client while the value proposition is still being established.

## Outcome ledger

For each consenting participant/cohort, keep: anonymous study ID, source, language, current alternative, task start, first useful action, first completed **human-recorded** session, second-session return, week-four active use, coach review response, support minutes, setup minutes, concrete continuation offer, decision and actual payment evidence. Store private research consent/contact information separately from this repository.

Local diagnostic events help explain save failures. Server rows confirm accepted transactions. Neither automatically proves a human trained: seeded data and automation are excluded. Review session activity against observation notes before making activation/retention claims.

Use the earlier predeclared decision thresholds, including actual repeat use and paid continuation. Do not shorten a four-week observation into a release check. Track denominators and nonresponse; do not select only successful participants.

## Codex iteration rules

- Fix a blocked task, lost work or misleading state immediately and rerun that scenario.
- If participants understand the interface but choose their existing workflow, examine the value proposition and switching effort before adding features.
- If plan setup dominates support time, compare a narrowly supported import format or a paid setup service against further editor complexity.
- If clients train but coaches do not review, identify whether the buyer values delivery alone before adding an inbox/reminder platform.
- If Arabic wording causes uncertainty, correct it with observed language usage and retest the same task.
- Expand organizations, billing, nutrition, AI or native clients only when measured demand supports the extra operating burden.

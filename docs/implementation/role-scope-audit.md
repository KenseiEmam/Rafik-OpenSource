# Original roles, organizational scope and revamp corrections

Reviewed 23 September 2026. **The current revamp does not yet implement the original organizational operating model.** Its R4 teams coordinate independent coaching relationships; they are not a replacement for an organization with its own administrators, trainers and trainees. This audit corrects the product and architecture baseline before further feature expansion.

## Evidence and limits

This is a source and recorded-schema audit, not a claim that every legacy screen worked in production. Sources:

- Original web: `RAFIK-FRONTEND` commit `a0c723e`. Paths and line numbers marked **W** below refer to that commit, not the replacement files now on `codex/revamp`.
- Original backend source: `rafik-api` commit `652e9ee`; the more complete deployed database/function evidence captured in the [live backend audit](../revival/06-live-backend-audit.md). **DB** references below are to [the captured schema](../revival/evidence/live-backend/public-schema.snapshot.sql), not a migration to execute.
- Original mobile: `rafik-mobile` commit `49390b6991e427baa851c2e6519ce403efe15c45`, marked **M**. Native source was inspected only.
- Original worker: `rafik-worker` commit `36fbd31dd4275c16017027b51c50d78f472f66db`, marked **J**. Its pre-existing `.DS_Store` modification is unrelated.

Reproduce web evidence with `git -C ../RAFIK-FRONTEND show a0c723e:src/router/index.ts` and the other W paths below. No retired hosting changes, outbound messages, legacy restoration or native edits were made for this audit. Current R7 browser checks establish the current implementation's tested behavior; they do not validate the organizational requirements identified here.

## Identity was shared; the business roles were distinct

Six product-role strings are referenced by the original clients: `Administrator`, `Trainer`, `Trainee`, `Organization Admin`, `Organization Trnr`, and `Organization Trnee`.

Legacy `users` stored a roles array, one nullable organization ID, separate trainee/trainer profile references and a separate `is_staff` flag. Roles were not mutually exclusive. This was one account system with separate business scopes, not six authentication systems. The one-organization field was a legacy limitation, not a reason to mix organization records with independent coaching.

- Ordinary mobile registration created `Trainee`; choosing trainer during profile completion wrote both `Trainee` and `Trainer` (M `lib/pages/authentication_profiles/register_account/register_account_widget.dart:631`, `complete_profile/complete_profile_widget.dart:983`).
- Organization-admin user creation explicitly wrote `Organization Trnee` for a trainee, or **both** `Organization Trnr` and `Organization Trnee` for a trainer. It set the organization and `is_staff`, created the appropriate profiles, then requested an invitation email (W `src/stores/user.ts:1073`). An organizational trainer could therefore also train within the organization.
- Organization admins could grant organization-prefixed roles to others in their own organization, including additional admins. Platform administrators saw the complete role list (W `src/components/SettingsTabs/RolesandPerms.vue:173`, `:245`, `:341`). There was no required sole-owner organizational role in this workflow.
- The web gate also relied on `is_staff`; a role name alone was not sufficient for entry (W `src/router/index.ts:348`, W `src/stores/user.ts:199`). Role edits did not synchronize this independent flag, creating inconsistent access states.

Legacy ownership was only partially expressed: program rows had organization IDs, but trainee data often lived in one global profile with one coach pointer. The new design must preserve the organizational business scope while fixing those ambiguous ownership/lifecycle boundaries. It must not reproduce the old schema wholesale.

## Legacy limitations and defects that are not requirements

1. **Role switches were scattered and inconsistent.** Sidebar visibility, route metadata, local-storage role substrings, `is_staff` and query filters could disagree. Several calendar/group/assessment routes required only authentication although their menu entries were more restricted. Role edits updated the array alone. The new API must define the capability once and the UI must consume it.
2. **Multiple-role precedence was inconsistent.** The home page chose CoachDashboard if either trainer role existed; an org admin/trainer could lose the admin landing page. Template listing tested org trainer before org admin, narrowing an admin/trainer to own templates, while assessment listing explicitly preserved admin scope (W `HomeVue.vue:67` under DashboardVues; `templatestores.ts:28`; `assessmentstores.ts:115`). Use explicit workspace/view selection, not accidental `if` order.
3. **Domain membership was not a complete enrollment workflow.** The [captured domain trigger](../revival/evidence/live-backend/database-functions/22-set-user-organization.sql) updated `users.organization` after insertion but did not grant organizational roles. Native registration separately inserted an ordinary trainee. No evidence establishes a reliable end-to-end claim of every pre-provisioned organizational account across these paths. Use verified invitations and clear pending/active states; do not auto-grant authority from an email suffix.
4. **The assignment setting had no demonstrated effect.** `trainer_assign` is edited in organization settings; the inspected application source does not read it to enforce assignment behavior. English says “Allow Trainers to Assign Trainees”; Arabic describes automatic assignment. Do not claim automatic allocation or silently recreate a no-op switch.
5. **Catalog behavior contained a hard-coded exception.** Native program list includes own organization OR trainer ID 7; its non-organization branch lists trainer 7 only. The organization getter returns zero for absence, so the `!= null` condition does not distinguish membership as intended (M `program_list_widget.dart:223`, `:748`; `lib/backend/schema/structs/user_struct.dart:107`). Free enrollment is conditional on trainer 7 in program detail (`:1424`). This is not a general public marketplace or a valid cross-organization permission.
6. **Program audit was partly decorative.** Accept/deny/reset buttons in the inspected audit detail have no click handlers (W `src/views/DashboardVues/AuditPrograms/ProgramDetails.vue:146–165`), while the trainer detail includes direct activation. Org program trainer filtering also queries the ordinary Trainer role (`Organizational/ProgramsList.vue:302`). Preserve a deliberate publication policy, not the appearance of an unimplemented approval system.
7. **Assessment multiplicity was incomplete.** Arrays support multiple trainees/assessors, but the performance trigger and several detail operations use the first trainee. The replacement needs per-participant results, unit/definition-aware comparisons and correction history. No generic percentage “performance” score or blind reuse of the old calculation.
8. **Admin analytics were not all real.** The admin dashboard hard-codes Enterprise Pro, seat counts, revenue, retention and performance percentages and displays a pie-chart image (W `AdminDashboard.vue:10–164`). Its upcoming assessments are fetched separately. Those static figures must not be presented as implemented analytics or real business evidence.
9. **Mobile organizational parity was not established.** Generated tables for groups/slots/assessments are not evidence of usable client screens. Inspected native interaction mainly follows own profile/program/coach, with the catalog organization branch above. Preserve the intended role contracts for the later mobile rebuild; do not certify the old mobile as complete.
10. **Old staff web intentionally rejected phone access.** The router redirected authenticated phone-sized views to the application route (W `src/router/index.ts:348`). The revamp must keep coach/admin web usable on phones; this legacy limitation should not return.

The already-known permissive RLS is not the focus of this audit. The missing distinction is also about ownership, workflows and useful interfaces; merely tightening permissions or renaming teams cannot fix it.

## Where the current revamp diverged

| Current implementation | Why it misses the requirement | Required correction |
|---|---|---|
| R4 team owner/admin/coach memberships | Organization trainees are not first-class members; independent relationships remain the center. A mandatory owner does not model multiple equal organizational admins. | Explicit organization membership with admin/trainer/trainee roles, lifecycle and organization-owned records. |
| Minimal team roster and private independent coach data | Appropriate for a collaboration overlay, insufficient for an organization operating its own training service. | Admin oversight of organization roster, assignments, organization-delivered training and assessment operations. Personal/independent records remain separate. |
| Consent-based handoff creates a new independent relationship and copies future plans | Internal staff replacement should not split the organization's trainee history into independent customer relationships. | Reassign the responsible trainer within the organization, retain organization-owned history and audit authorship, revoke departed staff access. |
| Personal plans copied into team snapshots | Shared copies are not an organization catalog with durable ownership and staff authoring. | Workspace-owned program drafts/versions, explicit authorship/editor access, internal catalog and reviewed delivery. |
| Generic coach/personal-training switch for every signed-in account | A UI destination is not a role. Organization admins need their own default view and navigation; trainer authority must not be implied by signing in. | Server-issued available contexts/capabilities; remember a valid context, handle revoked roles and guard deep links. |
| R2 assessment templates are client-response forms | They do not deliver scheduled assessor-led drills, attendance, multiple participants and recorded results. | Distinct assessment session model; reuse shared question/drill primitives only where semantics genuinely match. |
| R3 one-to-one availability/booking | Does not support an org admin coordinating staff, trainees/groups and assessments. | Organization calendar with explicit participants, assignment and collision/recurrence rules. |
| Coach progress and minimal team counts | Do not answer separate coach and organizational management questions. | Role-specific analytics built on the corrected ownership model and event/metric definitions. |
| No dedicated platform-administrator workspace | Local support tooling is not equivalent to user/organization operational administration. | Separate operator capabilities and operational surface; never elevate an org admin to platform admin. |

### Why this was missed and the process correction

The earlier scope reduced organizations to optional collaboration between independent coaches. The role names and legacy feature inventory were not traced through onboarding, ownership, user queries, assignment, calendar and assessment lifecycles before implementation. Tests then validated that reduced design. A passing team-consent test could not reveal that an organization trainee and an internal trainer reassignment were absent from the requirements.

For subsequent phases, start with **actor × organization/independent context × resource × lifecycle action**, and record both allowed and denied journeys before coding. Include an organization admin who is not a trainer, an admin/trainer, an org trainer who also trains, a person with separate independent/org contexts, a trainee with no assigned trainer, and a departing trainer. Trace each legacy job to retained/replaced/deferred/defective with evidence. No phase is organizationally complete because one team demo passes.

## Corrected target and implementation sequence

[ADR 0005](../decisions/0005-organization-and-independent-scopes.md) records the target decision. It is **planned architecture**, not implemented runtime behavior.

1. **R7 checkpoint:** retain the verified daily navigation/attention work as an incremental independent-coaching improvement. Do not claim its universal selector or team model as the final organizational UX.
2. **R7A, before R8 expansion:** implement the scoped identity/organization foundation in the requested Prisma/PostgreSQL server API. Move the backend transition earlier instead of adding more Supabase-specific organizational features. Port the existing command behavior to the new boundary in bounded feature slices, with one active backend at the completed checkpoint. Old production data needs no migration.
3. **R7A organizational operations:** organization invites, trainers/trainees/admins, memberships/roles, assignment and staff departure, organization ownership, scoped navigation and independent-context isolation. Tests must cover two organizations plus independent coaching, including the same identity in distinct contexts.
4. **R8 programming:** independent and organizational catalogs, clear authorship/publication, reuse, bulk delivery to eligible scoped recipients, optional program cover and useful program metadata. Rework the unshipped personal-only delivery draft against the new membership contract; do not apply its draft migration as an organization implementation.
5. **R9 service and analytics:** organizational scheduling/groups, assessor-led assessments with per-trainee results, coach service refinements, and distinct real analytics. No additional roles are needed solely to produce a chart.
6. **R10–R12:** scoped notification audiences and preferences, local operational/release readiness, observed usability/refinement. Platform operations must be covered in the operational phase. Native follows verified web/backend readiness. External providers, hosting, physical-device use and human outcomes remain separate evidence gates.

### Analytics and imagery implications

- **Independent coach:** own-client activity, completed versus eligible scheduled sessions, check-in response and review turnaround; filter by client/program/date and open the underlying work.
- **Organization trainer:** the same coaching measures restricted to assigned organization trainees, plus assigned assessment/calendar workload. Never include their independent clients or another organization's trainees.
- **Organization admin:** organization enrollment/activation, unassigned trainees, trainer workload/distribution, program participation, attendance and assessment completion/trends. Drill through to authorized organization records. These are operational and training measures, not invented revenue or health-outcome claims.
- **Platform administrator:** service/organization operations, not an automatic aggregation of private health data.
- Define time window/timezone, denominator, exclusions, historical assignment attribution, cancellation and late/corrected record handling. Supply chart labels and table alternatives; empty or insufficient data is an honest state. Avoid ranking trainer quality from raw workload or unequal trainee cohorts.
- Program covers are useful for recognition, but goal/level/duration/frequency/equipment provide the decision support. Internal organizational covers/catalogs inherit their organization's visibility. Public publication is a separate explicit action. One optional cover with a strong fallback comes before a gallery; instructional images belong with the exercise they explain.

## Acceptance required before declaring the correction implemented

- Org A admin can provision/manage A trainers, trainees and additional admins, inspect A operations, and assign/reassign A trainees without creating an independent-coach relationship. Cannot select B/independent users or content through search, forged IDs or bulk inputs.
- Org trainer sees assigned trainees and assessor duties; being staff in the same organization alone does not reveal every private conversation or independent record. Org trainee cannot gain staff tools through a URL or UI preference.
- Admin-only and admin/trainer accounts land in sensible, explicitly selected views. Trainer/trainee combined roles work without silently granting admin. Revoked roles disappear and stop server operations immediately, including stale tabs and pending commands.
- One identity's independent training/coaching data remains separate from its organization membership(s). Switching context scopes lists, counts, program selection, analytics, files, drafts, pending operations and notification links.
- Reassignment/departure preserves organizational training history, authorship, started prescriptions and exact retry behavior; former staff lose access and outstanding duties are visibly reassigned or unassigned. Last-admin removal has an explicit recovery rule.
- Calendar/assessment tests cover multiple trainees with distinct results, multiple assessors, attendance, conflict, cancellation, correction and permitted comparisons. Check-in tests remain separate.
- Coach/admin analytics produce different scoped results from known fixtures, including no-data, role changes and date boundaries. Every displayed numerator/denominator can be reconciled to authorized underlying records.
- Real role-specific journeys receive rendered/task review in English/Arabic, both themes, short/tall phone and desktop, plus failure/retry and keyboard states. Scope correctness and UX correctness are independent acceptance requirements.

Open product refinements (not permission to continue using the old team assumption): whether organizations need optional publication approval, whether trainers may self-assign unallocated trainees, and which organization performance aggregates are useful in actual operations. Start with admin-controlled assignment, author/admin-managed internal programs and fixed roles; add settings only when a real workflow requires them.

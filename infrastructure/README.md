# Infrastructure

`compose.yaml` is the repository's single Compose definition. Its default profile remains the local development PostgreSQL service. The `selfhost` profile runs the university-owned web, API, PostgreSQL, migration, mail and HTTPS reverse-proxy stack.

For self-hosting, copy `.env.selfhost.example` to `.env.selfhost` on the Unix server, set a unique lowercase `RAFIK_INSTANCE_ID`, unique random 64-character hex PostgreSQL/API passwords, and the public domain, then point DNS to the server. The instance ID names its Compose project and volumes, so choose a different value for each institution sharing one Docker host. Keep the service on a private network until the first person completes super-admin setup; that first account receives administrative access. Run `bash infrastructure/scripts/deploy.sh` to build and start the self-hosted stack. Inspect with `docker compose ... ps` and `logs -f api` (review logs before sharing). PostgreSQL stays on an internal Docker network. `bash infrastructure/scripts/backup.sh` makes a paired checksummed database/private-file backup; `bash infrastructure/scripts/restore.sh infrastructure/.env.selfhost <backup-directory>` restores that pair. The API is paused while these commands run. Backups need to be encrypted and copied to university-controlled off-host storage. Run the matching database migration once before restoring onto a clean instance. These operations have not yet been integration-rehearsed; do not treat the deployment as release-ready until Stage 3 gates are verified.

For local development, use the root workspace commands (`npm run backend:start` and `npm run backend:stop`) so migrations and local service lifecycle stay consistent. Never use local sample identities or synthetic credentials for hosted deployments.

Optional single-VM Terraform starters for AWS, Google Cloud and Azure are listed in the [cloud deployment guide](cloud/README.md). They prepare the same Compose stack and have not been applied or verified against provider accounts.
